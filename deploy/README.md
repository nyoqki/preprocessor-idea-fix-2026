# Автодеплой «Ясно»

Push в `main` запускает `.github/workflows/ci.yml`: Python-проверки и frontend → сборка и публикация Docker-образа → `deploy`. Обновление сервера начинается только после успешных проверок и сборки. Pull requests и теги сервер не обновляют.

В production используется образ `ghcr.io/nyoqki/preprocessor-idea-fix-2026@sha256:…`, полученный из output того же CI run. Сервер проверяет метку `org.opencontainers.image.revision` против SHA коммита. Тег `latest` для выбора релиза не используется. Старый workflow, для которого `main` уже продвинулся вперёд, пропускает деплой. Деплои последовательные; новый push не отменяет обновление посередине.

## Сервер

Текущий адрес: `admin@207.2.120.48:23971`, проект `/srv/yasno`, Compose project `yasno`. Конфигурация окружения остаётся на сервере; workflow не переносит и не выводит `.env`.

`deploy/release.py` устанавливается как root-owned `/usr/local/sbin/yasno-deploy`. В `authorized_keys` отдельный ключ GitHub Actions имеет ограничение:

```text
restrict,command="/usr/local/sbin/yasno-deploy" ssh-ed25519 <public key> yasno-github-actions-deploy
```

Этот ключ не открывает shell, SFTP, PTY или туннель. Принимается только `deploy <SHA из 40 hex-символов> <sha256:64 hex-символа>`. Допустимый image repository зафиксирован в серверном скрипте.

`deploy/known_hosts` содержит публичный ключ сервера, полученный через уже доверенное SSH-соединение. Actions использует `StrictHostKeyChecking=yes`; при смене серверного ключа pin нужно обновить после проверки нового ключа.

Единственный repository secret — `YASNO_DEPLOY_SSH_KEY`, приватная часть отдельного ограниченного ключа. Приватный ключ в репозиторий не попадает. Для чтения приватного GHCR workflow передаёт свой краткоживущий `GITHUB_TOKEN` с `packages:read` через зашифрованный stdin SSH. Он не появляется в аргументах команд и хранится в отдельном временном Docker config, который удаляется сразу после pull. Постоянный PAT на сервере не требуется.

## Обновление и восстановление

Сервер блокирует параллельные обновления, скачивает конкретный digest, проверяет revision и определяет существующие процессы. Затем:

1. Сохраняет прежние image IDs и закрепляет их rollback-тегами.
2. Создаёт приватный `pg_dump -Fc` и конфигурацию отката в `/home/admin/backups/yasno-auto/<timestamp>-<sha>/`.
3. Выполняет миграции одноразовым контейнером нового образа.
4. Обновляет API и worker; poller обновляется только если он уже существует. Сохранённый `compose.poll.yaml` сам по себе не включает удалённый poller на webhook-сервере.
5. Ожидает состояние контейнеров, проверяет `/readyz` и соответствие всех процессов одному image ID.
6. Только после успеха обновляет локальный тег `yasno:local` и `/srv/yasno/.deploy/current.json`.

Если миграция завершилась ошибкой, прежние процессы продолжают работать. Если ошибка возникла при переключении или readiness, скрипт восстанавливает **отдельный предыдущий образ каждого сервиса**, проверяет readiness и завершает CI с ошибкой. Повтор успешно завершённого деплоя не выполняет миграции заново.

Автоматический откат восстанавливает контейнеры. Он не выполняет обратные миграции базы. Миграции должны сохранять совместимость с предыдущим релизом; для ручного восстановления данных остаётся `database.dump`. Файлы storage и контейнеры PostgreSQL/Redis при деплое не пересоздаются.

## Проверка и обслуживание

```bash
uv run pytest tests/deploy -q
bash -n deploy/github-actions.sh
```

Тесты проверяют отказ от посторонних SSH-команд, отсутствие токена в аргументах, соответствие image/commit, переключение всех процессов, идемпотентность, сохранение webhook-режима и откат после ошибки readiness/миграции.

После изменения host-скрипта требуется его установка администратором:

```bash
sudo install -o root -g root -m 755 deploy/release.py /usr/local/sbin/yasno-deploy
```

Серверный helper отделён от приложения и не заменяет себя кодом из входящего Docker-образа. При изменении host/port/user обновляются `deploy/github-actions.sh` и `deploy/known_hosts`. Диагностика последнего успешного релиза — `/srv/yasno/.deploy/current.json`; состояние не содержит registry token или `.env`.
