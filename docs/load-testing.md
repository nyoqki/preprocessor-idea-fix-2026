# Нагрузочный прогон API и проверка восстановления

Этот протокол относится к HTTP API мини-приложения и приёму webhook,
с настоящими PostgreSQL и Redis в отдельном Docker-контуре.
Скрипт: [tools/load/check.py](../tools/load/check.py),
окружение: [compose.yml](../tools/load/compose.yml).

## Что именно проверяем

1. После прогрева последовательно держим 5, 20, 50 и 100 одновременных запросов
   по 20 секунд на ступень: профиль, карта пробелов, активный тест.
   Авторизация использует правильно подписанные синтетические initData;
   обработчик действительно обращается к БД, включая обновление `last_seen_at`.
   У каждого из 100 учеников три темы по две ошибки: 300 записей прогресса
   и 600 ошибок; карта возвращает данные, а не пустой ответ.
2. Для 100 учеников отправляем 300 разных ответов по пять раз: всего 1500 POST,
   до 50 одновременно. Проверяем сохранённые данные: 100 завершённых тестов,
   ровно 300 успехов, по три на ученика. Повтор не должен увеличить счётчик.
   Исходные 600 ошибок должны сохраниться без изменений.
3. Отправляем 100 разных обновлений webhook по десять раз: 1000 POST,
   до 100 одновременно. Сверяем точные ID 100 новых задач в Redis.
4. Останавливаем Redis. `/readyz` и webhook должны вернуть 503. После запуска Redis
   API должен восстановиться без собственного перезапуска и снова принимать webhook.

В каждом ответе чтения проверяется также структура или принадлежность данных,
а не только статус HTTP. Время измеряется от отправки до чтения тела ответа.

## Критерии принятия, заданные до замера

- Во всех нагрузочных ступенях — ноль сетевых ошибок, неожиданных статусов
  и неверных проверяемых ответов.
- Для чтения при параллелизме 5 и 20 — p95 не более 1000 мс.
- Для повышенной нагрузки 50 и 100 — ноль ошибок и сохранность данных;
  задержки публикуются отдельно, обязательный порог скорости для них не задан.
- Результат повторных ответов и дедупликации должен совпасть с ожидаемым в БД/Redis.
- Во время отказа Redis ожидается 503, после восстановления — 200;
  у API не должно быть перезапусков или OOM.

Порог 1000 мс — внутренний ориентир команды для API без AI,
**не SLA из правил хакатона**. p95 — время, в которое уложились 95% измеренных
запросов; p99 и максимум также сохраняются в JSON. Ожидаемые 503 при выключенном
Redis учитываются как отдельный эксперимент, а не прячутся среди успешных запросов.

## Обнаруженные транспортные сбои и контроль параметров

Первый полный прогон с заполненными картами сохранён в
[load-results-initial.json](load-results-initial.json): чтение и webhook без ошибок,
но **2 из 1500 отправок ответов завершились транспортным сбоем**.
Критерий нулевых ошибок не выполнен, `passed: false`.
Все 100 тестов завершились, счётчики в PostgreSQL остались верными.

В [укороченном диагностическом прогоне](load-results-diagnostic.json) ошибка
воспроизвелась один раз: `RemoteProtocolError: Server disconnected without sending
a response.` Это установленный тип сбоя; точная причина пока не доказана.

Гипотеза — гонка повторного использования соединения на границе idle timeout:
у [HTTPX](https://www.python-httpx.org/advanced/resource-limits/) и
[Uvicorn](https://uvicorn.dev/settings/#timeouts) значение по умолчанию — 5 секунд.
Для контрольного прогона idle expiry клиента уменьшен до 2 секунд.
Параллелизм, длительность ступеней, таймаут запросов, приложение и критерии
принятия сохранены. Автоматических повторов запросов в генераторе нет.

Это изменение параметров нагрузочного клиента, а не исправление серверного кода.
Даже успешный контрольный прогон не доказывает, что исходная проблема полностью
устранена: для этого нужна трассировка закрытия соединений и повторные наблюдения.
Параметр клиента записывается в новом JSON; первые два отчёта используют исходные
5 секунд. Сохранность счётчиков объясняет, зачем ответы идемпотентны и интерфейс
поддерживает повтор при неоднозначном результате POST.

## Условия и границы вывода

- Контур локальный: loopback, один процесс API с лимитом 2 CPU / 1 ГиБ;
  PostgreSQL — 1 CPU / 512 МиБ, Redis — 0,5 CPU / 128 МиБ.
  Генератор нагрузки работает на том же хосте и конкурирует за его ресурсы.
- Используется закрытая модель: число одновременных запросов постоянно,
  следующий начинается после завершения предыдущего. При замедлении сервиса
  интенсивность поступления падает. Поэтому полученный RPS нельзя выдавать
  за гарантию выдерживания произвольного фиксированного потока.
  См. [различие моделей в документации Grafana k6](https://grafana.com/docs/k6/latest/using-k6/scenarios/concepts/open-vs-closed/).
- Это короткий прогон с повышением параллелизма. Обычная школьная нагрузка
  ещё не измерена, предел пропускной способности и длительная работа не установлены.
  См. [условия стресс-тестирования](https://grafana.com/docs/k6/latest/testing-guides/test-types/stress-testing/).
- Worker не запущен: измеряются приём и дедупликация задач, **не их обработка**.
  Фотографии, SymPy и AI в эту нагрузку не входят. Реальный AI проверялся
  [отдельно](verification.md#настоящие-ai-запросы).
- Синтетические initData проверяют контракт подписи. Настоящий MAX-клиент,
  интернет, HTTPS, доставка сообщений, рукописные фото и лимиты провайдера
  этим прогоном не проверяются.
- В контуре только искусственные пользователи и ключи; `.env` проекта не передаётся
  в контейнеры. MAX API направлен на закрытый локальный порт; AI_FAKE включён.
  Исходящий доступ не блокируется сетевым экраном, но сценарий не вызывает MAX/AI.

Корректный вывод: «На указанном локальном контуре API прошёл такие-то ступени
и проверки данных». Формулировки «выдерживает любое число учеников» или
«вся система с ИИ работает с этой скоростью» из этого эксперимента не следуют.

## Как воспроизвести

Из корня проекта, Docker Compose v2 и Python 3.13:

```bash
uv sync --locked
docker build -t yasno:strict-audit .
docker compose -f tools/load/compose.yml up -d --wait
uv run python tools/load/check.py --duration 20 --fault-test
docker compose -f tools/load/compose.yml down -v
```

На этом хосте для сборки потребовался `docker build --network=host` из-за DNS
BuildKit; это свойство окружения, а не требование к приложению.
Для уже собранного образа можно задать `YASNO_LOAD_IMAGE` перед запуском Compose.
На время проверки нужны свободные порты 55433, 56380 и 58001 на loopback.

`--fault-test` останавливает **только Redis проекта `yasno-load-check`**.
Он не затрагивает рабочий сервер и другие Compose-проекты. `down -v` удаляет
одноразовую базу и очередь; JSON-отчёт остаётся в репозитории.
Не запускайте этот сценарий на production и не подставляйте реальные токены:
скрипт намеренно использует фиксированные локальные адреса и синтетические данные.

Исходную конфигурацию клиента можно проверить отдельно:

```bash
uv run python tools/load/check.py --keepalive-expiry 5 --output /tmp/yasno-load-keepalive-5.json
```

Сбой не обязан воспроизводиться при каждом прогоне. Сравнивать следует отчёты
с одинаковыми длительностью и параллелизмом, учитывая общий хост генератора и API.
